# Reporting framework noise upstream

The framework reminds; the session decides what fits this project (AGENTS.md). When a piece of guidance, a step or a check got in the way here, and would get in the way of projects like this one, report it to the framework so the next project does not meet it.

## When

- It stated one answer where this application needed another, and research or what you know showed why.
- It repeated itself, or asked for paperwork that decided nothing.
- A step did not fit how this kind of application works, and you set it aside (development/STEPS.md).
- A check failed on how something was written, or on a layout or tool the project does not use, or it let through something it should have stopped.
- It named a technology. The framework names none; each project chooses its own.

A gap counts too: something the framework should have reminded you of and did not.

## What to write

- The file and section, and what it asked.
- What happened, in general terms: the kind of application, not its name.
- Why it did not fit, with the evidence or the research behind that.
- What you did instead, and how it was verified.
- The change you propose: the words to remove, soften or add. A pull request can carry the exact text.

Keep out the project's name, the names of its owner and its customers, its data, code, paths and credentials, and anything else private. The framework's repository is public.

## Where, and who sends it

The framework's source is the Source line in VERSION-LOG.md. Draft the report as an issue or a pull request there and show it to the owner. Send it only with the owner's approval, because it publishes outside the project (#29). If the owner declines, keep the draft with the project's records and mention it in the session summary.

A report does not change this project's obligations. Keep working to the decision you recorded; the framework's answer arrives through development/UPDATE.md.
