# Convention B6: File Handling (Server-Side)

For the client side of transfers, see universal convention #9.

## Applies when

The service accepts, stores or serves files. What varies: file sizes and counts, whether the server must inspect or transform files, where they are stored, and who may read them.

## Principle

Files go through one storage service, and the server decides everything that matters about them: where they are stored, under what key, what type they really are, and who may read them. Nothing the client declares about a file is trusted. The transfer path is chosen for the files: straight to storage when they are large and the storage supports it, through the server when it must inspect or transform them or when they are small.

## Reusable System

The storage service: one interface for storing, reading, deleting and issuing short-lived access; the key scheme, generated by the server; the validation of content, size and, where the facts call for it, malware; and the transfer path. References.md records each; § Boundaries keeps features from calling the storage provider directly.

## Rules

- Generate storage keys on the server. Never let the client choose the path.
- Check the file's real type from its content, never from its name or its declared type.
- Check size on the server, even when the upload path already limits it.
- Choose the transfer path from the files and the storage, and record it. When files go straight to storage, the server issues a short-lived, narrowly scoped upload address and validates the file after the upload, before recording it.
- Keep access addresses short-lived, and issue them only after checking who may read the file (#24).
- Features use the storage service, never the provider's library. Changing providers, or using local storage in development, changes one place.

## Violations

- A key or path taken from the client, allowing traversal into other files.
- A type check that trusts the name or the declared type.
- The storage provider's library called from many handlers.
- Large files streamed through a server that neither inspects nor transforms them, tying up its processes.
- A long-lived public address for a private file.

## Wrong vs Right

- WRONG: the server accepts the client's file name as the storage key, and a crafted name reaches outside the upload area. RIGHT: the server generates the key and records the original name only as data.
- WRONG: a file declared as an image is accepted because its declared type says so, and it is a program. RIGHT: the server reads the first bytes and compares them with the signatures of the allowed types.
- WRONG: every large video passes through the application server on its way to storage, and uploads stall it. RIGHT: the server issues a short-lived upload address, the client uploads straight to storage, and the server validates the result before recording it.

## Research Notes

Research the storage options for the chosen hosting, how they issue short-lived upload and download addresses, content-signature checking for the file types the product accepts, malware scanning when the facts call for it, and how to put storage behind one interface. Record the storage service, the key scheme, the transfer path and the validation in References.md, and the boundary in § Boundaries.
